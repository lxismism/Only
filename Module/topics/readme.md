topic实现是整份代码最复杂的，它的函数调用调了一层又一层，不仅函数，指针也是调用了一层又一层，而且还不是在同一时间调用到指针的底部，而是指针先调一个成员，然后在下一个函数里面调这个成员的成员，甚至再在下一层函数调用这个成员的成员的成员。所以导致topic一个文件夹的可读性对第一次研究这个框架实现的小白非常不友好，你都不知道从哪里开始。

而在topic实现内部最复杂的部分，便是字节流管道传输机制，它是怎么一回事呢？

大家都知道，我们的目的是：把不同topic发布的不同的自定义结构体类型的数据，以同一种方式，送到subscriber手上，并且要求最后送到subscriber手上的数据，与topic发布的数据是同一个结构体类型，并且内容是完全一致的

如何把不同类型的自定义结构体用同一种方式传输，最后再拿到与发布者一样的结构体数据呢？

那几个关键的逻辑节点在与：自定义结构体T->同一种方式->自定义结构体T

在本实现中，数据的形式经历了如下过程：

自定义结构体T-------->字节流------->自定义结构体
            序列化          反序列化
